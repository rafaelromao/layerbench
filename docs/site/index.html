Keyboard layout analyzer for ZMK keymaps

Scores the keys you actually press.

LayerBench types a text on your keymap the way ZMK would — layers, one-shots, adaptive and repeat keys, combos, macros — and measures SFB, SFS, scissors, rolls and Effort on the presses that result.

Most analyzers score one letter on one key

That fits a 30-key layout. It doesn't fit many ZMK keymaps: a thumb opens a second alpha layer for the next key, an adaptive key types what the letter before it calls for, a combo types a letter no key has, a macro types qu and hands the next key to another layer.

Some analyzers approximate parts of this, by rewriting the text before scoring it or by charging a cost for each modifier; the comparison says which. LayerBench simulates the keymap instead, press by press, each on the layer it lands on, and scores what was pressed.

ação on Magic Romak, in four presses

With multi-letter macros switched off, the same word takes five presses: a, the thumb, ç, ã and o. The simulator's tests pin traces like these. Type any word in How is this typed?

What no other analyzer we checked does

Five other analyzers, checked against their documentation and code on 7 October 2026. The comparison has each of them, row by row, with sources.

  • Adaptive keys, as many as you have

    Each with its own rules, chained, on any layer, typing one letter or several. Elsewhere we found one at most.

  • Repeat and alternate repeat

    Pressed as your keymap presses them, rather than rewritten into the text before it is scored.

  • Combos per layer, macros of several letters

    A chord that types a letter no key has, accents the next one or opens a layer, on the layers it works on, and does something else when held; a key that types qu and hands the next key to another layer.

  • Your firmware keymap, read in

    keymap-drawer's YAML of a ZMK or QMK keymap, layers and combos included. None of the others reads one.

  • The presses behind any word

    Type a word and the board plays it, press by press, on the layer each lands on, and counts the presses it took.

  • Metrics you compose

    Every rule is data: switch it off, move its thresholds, or write a new one, in the browser. Elsewhere, weights in a file, or new code.

  • One link to the analysis

    The layout, saved or never saved, the bundled text, the preset and every switch, in an address you can send.

Your keymap, not a letter map

The simulator follows ZMK's rules for what a press does, and every behavior below is part of how a text is typed.

  • &mo &lt

    Layers while a key is held, and layer-taps.

  • &sl

    One-shot layers: the next press lands there, then the layer is released.

  • &tog &to

    Toggled and exclusive layers, locking the way ZMK locks them.

  • conditional layers

    A layer that comes on while the layers it depends on are all on.

  • &sk

    Sticky shift, and sticky modifiers that combine.

  • &caps_word

    Caps word, until a key outside its list.

  • &key_repeat

    The repeat key, and alternate repeat, which types something else after some keys.

  • adaptive keys

    Adaptive keys, whose output depends on the key before: as many as the keymap has, chained if it chains them.

  • combos

    Chords, only on the layers they are for: one more way to a letter, an accent or a layer, and another when held.

  • &macro

    Macros that type several letters, open a layer, or call other macros.

  • mod-morph tap-dance dead keys Unicode

    Modeled too.

Layer taps, holds and one-shots are presses too, and the layer metrics say what they cost: layer taps per 100 symbols, wasted one-shots, adaptive key hit rate, and extra keystrokes per symbol.

What you can do with it

Rank with, or without

The Library ranks every layout on the same text, by Effort or SFB, with both on every card. Untick adaptive keys, the repeat key, typing combos or multi-letter macros, and each layout is ranked as it types without them: what each feature is worth, in two numbers. A card also says how much of the text a layout can't type.

Compare two layouts

Every number side by side, with the difference and which of the two does better. Compare with types both without the same features, so the comparison stays fair.

Edit where it is analyzed

Select a key and choose what it does: a symbol, a layer, a tap-hold, an adaptive key, a macro. Or type it in ZMK's own syntax, like &lt num a. Every number follows the edit, and the key shows its own part of each. Drag one key onto another to swap them; a plain swap shows an estimate at once, and the full numbers follow.

Rules are data

Every rule cites its sources. Switch one off, move its thresholds and bands, weight it, or compose a new one from predicates, and save the set. Presets follow the Keyboard Layouts Doc, cyanophage's playground and Keysolve.

On a phone too

Analyze, its editor and the Library fit a phone. The editor keeps the board in sight while a key is changed, and its controls are sized for a finger.

  • Bring your keymap

    Import a keymap-drawer YAML file — keymap-drawer reads ZMK and QMK keymaps — and choose which layers to take. Export one back, or LayerBench's own JSON. A three-row text layout works too.

  • Your language, accents intact

    English, Brazilian Portuguese, Spanish, French and Italian, as news. Mix two texts, or paste your own and save it. ã and ç are letters in their own right, and a layout that can't type them ranks after one that can. Every layout here types them, most through a Dead keys layer one combo away. Missing your language? Add a text by pull request.

  • Share the link

    The address carries the analysis: the layout, saved or never saved, the bundled text, the preset and every switch. A saved text or rule set opens only where it is stored.

  • Keep it yours

    Duplicate a layout, start one, or import yours, then Save it: it joins the Library, ranked with the rest. It is kept in your browser; sign in with GitHub under Storage to keep it in your own account too, in your fork of layerbench, which is public as the repository is, or in secret gists, which are unlisted rather than private. Why you can trust the numbers

A number is only useful if it means what it says. This is what stands behind LayerBench's, and where in the source to look.

  • Every rule cites its source

    Each rule names where its definition comes from — the Keyboard Layouts Doc (3rd edition), cyanophage's playground, Keysolve, Genkey, ZMK's documentation — and a test fails if one doesn't. Where the Doc is silent, as it is on layer taps, adaptive keys and combos, the rule says it is a LayerBench addition, and the metric glossary explains how it counts.

    In the source: packages/core/src/rules/references.test.ts

  • The numbers are pinned

    Reference reports — a few layouts on a few texts, under more than one preset, with and without space, and with shift modelled — are checked on every change: each rule's value to a millionth of itself, and every list and every trace exactly. Each deliberate change to a number is logged with its reason.

    In the source: packages/core/src/golden/reports.test.ts, packages/core/golden/GOLDENS.md

  • The firmware's rules are tested one by one

    A one-shot layer is consumed by exactly one press, and one wasted on a modifier is counted. Toggles lock. Conditional layers settle. A combo fires only on its layers, and can open one. A macro can open a layer. The first matching branch of an adaptive key wins. Caps word ends where ZMK ends it.

    In the source: packages/core/src/sim/machine.test.ts, packages/core/src/sim/resolver.test.ts

  • It shows its work

    Every analysis says which text and rules it used, and whether space and case were counted. How is this typed? shows the presses behind any word. The Library says how much of the text each layout can't type, and the Corpus view where each text comes from.

  • Private by construction

    No account of ours, and no analytics. The app is static files; the only server code is a small worker that signs you in with GitHub and keeps nothing. The app's content security policy lets it talk only to itself, to api.github.com and to that worker; a token is never put in a link, an export or an error. This page loads nothing from anywhere else and runs no JavaScript.

    In the source: apps/web/vite.config.ts, apps/web/src/server/github-auth.test.ts, apps/web/src/storage/github-api.ts, apps/web/src/storage/github.test.ts

  • Checked on every change

    Formatting and lint, a strict type check, the unit tests and a production build run on every pull request and every push to main, and only an app build that passes them is published.

    In the source: .github/workflows/ci.yml

What the numbers assume

  • Timing isn't modeled: tap-holds never misfire, combos always fire, one-shots end at the next key and never time out, and an adaptive key's idle window is always met. The keymap is typed as you mean it.
  • When a character can be typed more than one way, the cheapest way is taken — fewest presses, then fewest same-finger pairs, then least effort — unless you set the order in Typing paths. Where several keys tap the same layer, each word uses the one that gives it the fewest same-finger pairs.
  • The text is read left to right, taking the longest piece one key or combo can type from where you are — qu before q — without looking ahead, and never splitting it again.
  • Space presses, numbers and most symbols are left out, pairs don't cross words, and case is folded, unless you switch them on.
  • Pairs are a share of the text's own pairs, and Effort is per character typed, spaces included, not per key press, so layer taps and holds can't thin either number out.

When another tool is the better choice

  • You want a layout generated for you. LayerBench analyzes; it doesn't optimize. Oxeylyzer, Dario Götz's optimizer, Jalo and keycraft do, and Mana2 says it does.
  • Your layout is one layer of 30 keys. cyanophage's playground is instant, and its numbers are the ones the community quotes.
  • You want to browse thousands of layouts. cmini and AKLDB, akl.gg and Emulayout have them.
  • You want scores from your own typing speed. Trialyzer uses trigram speeds you measure yourself; LayerBench has no timing model.
  • You need a language we don't ship. cyanophage has 14, and Oxeylyzer has rules for about 30 if you bring the text.

Also worth knowing

  • Keysolve, which the Keyboard Layouts Doc points to for scissor stats; inactive since 2023.
  • Genkey, an analyzer and generator that now points its users to Oxeylyzer.
  • KLA and KLAnext, the classic web analyzer and its continuation.
  • Jalo, an analyzer and optimizer whose metrics follow the Keyboard Layouts Doc.
  • keycraft, an analyzer, ranker and optimizer.
  • Kawalyser, a spreadsheet that handles a magic key, a repeat key and a dead key.
  • Emulayout, to filter and try community layouts, magic ones included.
  • keymap-drawer, which draws ZMK and QMK keymaps; LayerBench reads and writes its YAML.
  • The Keyboard Layouts Doc, the community's reference for what the metrics mean, and layouts.wiki.

Start in four steps

  1. Pick a layout

    The Library first opens ranked by Effort. Choose one, or bring your own from a keymap-drawer file.

  2. Read two numbers

    Effort is how hard the keys are to reach, and SFB how often one finger presses two keys in a row. Lower is better for both.

  3. Change a key

    In Analyze, select a key and choose what it does. Every change is kept as you make it, every number follows it, and Undo takes it back.
